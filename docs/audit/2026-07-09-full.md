# Audit report — full sweep — 2026-07-09 — 81bdebe
Agents: audit-security, audit-tenancy, audit-data, audit-pipeline, audit-api-contract, audit-architecture, audit-compliance, audit-devops, audit-tests, audit-frontend-arch, audit-design-system, audit-ux-flows, audit-a11y, audit-frontend-perf (all 14 ran) · Skipped: none. audit-a11y and audit-frontend-perf ran static-only (no served build, disclosed by both); audit-data and audit-tests ran live read-only probes / test suites against the dev database (`.env.local` `DATABASE_URL`, EU dev project, synthetic data only).

## Executive summary

The platform's engineering core is in good shape: the pipeline is pure and deterministic, tenant scope-builder discipline is followed almost everywhere, secret handling and the non-production email sink are airtight, and the primary weekly-job flow works end to end. Two problems, however, are serious enough to block the Phase 2 distribution gate. First, the manual lead-assignment feature (added in database migration 0009) shipped without a decision record and with a real cross-partner data leak: when an administrator re-routes an already-matched lead from one partner to another, the original partner keeps full visibility of the seller's personal information and can still change the lead's status. Second, the automated test safety net has holes at exactly the wrong moment — the required end-to-end partner journey test (TST-07) still does not exist, the integration test suite has been silently failing for nine commits (nobody has run it with credentials since a page rename), and the new admin lead screens shipped with zero tests. Beyond those, the application is not yet deployable: there is no scheduled job to send partner emails, error reporting (Sentry) is parsed but never wired, and the file-upload path has no timeout accommodation for large files. Several correctness and consistency issues cluster around the same manual-assignment feature (the "who owns this lead" question is answered three different ways across visibility, analytics, and the Excel export). A broad set of user-experience and accessibility gaps — silent save failures, failures shown as "nothing here," a keyboard-unreachable primary workflow, and text that fails contrast standards — round out the high-severity list. Compliance evidence has gaps too: partner invites and admin-forced sign-outs are not written to the audit trail, and a demo-data script actually deletes audit rows. There is no prior audit report to compare against, so this establishes the baseline. Note that this branch is 17 commits ahead of its remote, so continuous integration has never run against this code.

## Top risks (ranked)

### TR-1 — Manual-assignment / admin-edit overlay: cross-partner PII leak, three-way ownership, stale audit backstop, unspecced edits
- **Severity:** Critical
- **Verdict:** SPEC-VIOLATION
- **Refs:** PRN-08, PRN-13, PRN-15, PRN-05, SEC-01, ADM-02, DM-01, ADR-0013 · OWASP API1:2023 (BOLA), A01:2021
- **Agents:** audit-tenancy F-1, audit-architecture F-1/F-2/F-3, audit-data F-1/F-4, audit-api-contract F-7 (activity facet)
- **Evidence:**
  - `src/lib/scope.ts:41-43` — `partnerOwnsLead` is `or(eq(partnerId,me), eq(manualPartnerId,me))`; its comment asserts the two "never overlap." `src/modules/leads/commands.ts:177-196` (`editLead`, `action:"set"`) writes `manualPartnerId` on **any** kept lead with no unmatched guard (contrast `manuallyAssignLead` at `:55`). Reachable via admin PATCH `src/app/api/leads/[ref]/route.ts:57-69` and the dialog `src/app/leads/lead-dialog.tsx:314,367`. Result `partnerId=X, manualPartnerId=Y` → `partnerOwnsLead(X)` still true → partner X keeps seeing/mutating the re-routed lead (seller PII, notes, status, export). `tests/integration/isolation.test.ts:117-122` only covers the safe unmatched→manual case.
  - Owner computed three incompatible ways: visibility `OR` (`scope.ts:41`), display `coalesce` (`leads/queries.ts:117`, `getAdminLeadDetail:218`, `analytics/queries.ts:152`), and `partnerId`-only for the Excel deliverable + run summary (`run/export-data.ts:41,63`) and `analyticsOverview:47`/`periodSummary:111`.
  - RLS backstop never updated: `leads_scope` + 3 dependent policies (`0001_rls_and_constraints.sql:126-167`) key on `partner_id` only; `0009_manual_assignment.sql` shipped no policy change (confirmed live via `pg_policies`), despite the commit claiming "leads RLS already covers the new columns."
  - `editLead` rewrites `address/city/state/zip` (`EDITABLE_COLUMNS`, `commands.ts:133-147`) without recomputing `dedupeKey`/`addressNormalized` (`pipeline/normalize.ts:75-80`), so future dedupe/PRN-05 "revert to original" silently drifts.
- **Impact:** An admin correcting a lead's routing leaves the prior partner with full access to another partner's seller PII — the exact leak this audit exists to prevent. Secondary: the same lead can appear as belonging to different partners on the portal, the dashboard, and the downloaded Excel; and address edits break future dedupe.
- **Remediation:** (1) Define the effective owner once and use it everywhere: `partnerOwnsLead(me) = coalesce(manual_partner_id, partner_id) = me` in `scope.ts` (equivalently the `isNull` form in audit-tenancy F-1). (2) Add TST-01 case: seed `partnerId=X, manualPartnerId=Y`, assert X excluded / Y included. (3) Ship migration 0010 updating the four RLS policies to `... OR manual_partner_id = app_current_partner()` (including the `lead_id IN (...)` subqueries). (4) Export one `effectiveOwnerId` SQL expression and route `getRunExportData` grouping, `computeRunSummary`, and the analytics functions through it. (5) Recompute `dedupeKey`/`addressNormalized` in `editLead` on address/zip change (or ADR the alternative). (6) Fix `listPartnerActivity` to use `partnerOwnsLead`. (7) Record ADR-00xx (effective-owner overlay) and ADR-00yy (admin lead correction scope).
- **Effort:** Scope+RLS fix S (land now); analytics/export unification + editLead ADR M (Next WP). **WP candidate:** yes for the unification + ADRs.

### TR-3 — Rule evaluation order is not pinned: identical `rulesHash` can produce different output
- **Severity:** High
- **Verdict:** SPEC-VIOLATION
- **Refs:** PRN-01, DM-08, TST-05, MLS-05 · deterministic-replay
- **Agents:** audit-pipeline F-1 (+F-2 golden gap)
- **Evidence:** `src/modules/run/rules.ts:27-32` — the four rule `SELECT`s have no `ORDER BY`; engines are first-match-wins (`pipeline/recode.ts:19-27`, `mls.ts:51-67`) but the snapshot hash is order-independent (sorted, `snapshot.ts:42-51`). ### TR-9 — UI silent failures: saves fail with no signal; errors render as "nothing here"
- **Severity:** High
- **Verdict:** SPEC-VIOLATION
- **Refs:** NTS-02, FRM-05, UXQ-01, PTL-03, FRONTEND_STANDARDS §8 · Nielsen "visibility of system status", WCAG SC 4.1.3
- **Agents:** audit-ux-flows F-1, F-2, F-3; audit-a11y F-6, F-7 (announcement facet)
- **Evidence:** `NotesPanel.tsx:34-62` add/edit mutations define no `onError` (mounted on 3 note streams, both roles); same in `portal/devices/page.tsx:30-39` (Sign-out fails silently). App-wide `data?.x ?? fallback` with no `error` check: `NotificationBell.tsx:36-42` ("all caught up" on failure), `AppShell.tsx:111-116` (unmatched badge reads 0), `dashboard/page.tsx:85-94` (attention banner), and several portal pages. `portal/leads/[ref]/page.tsx:44-70` shows an infinite skeleton on query error (`!data` never clears). Screen-reader gaps: note "Saved ✓" (`NotesPanel.tsx:90-94`) and the bell's unread count (`NotificationBell.tsx:66-81`) are not in `aria-live` regions.
- **Impact:** Users lose notes believing they saved; a degraded backend reports a false "all clear" — worse than no signal — on the mechanisms admins and partners rely on to know something needs attention.
- **Remediation:** Add `onError` toasts/inline text to every mutation (keep the unsaved draft); destructure `error` on every `useQuery` and branch `loading → error → empty → success` (reference: `portal/activity/page.tsx`); add visually-hidden `aria-live` regions for save and unread-count.
- **Effort:** M (wide but mechanical). **WP candidate:** yes ("state-matrix hardening pass").

- **Severity:** High
- **Verdict:** SPEC-VIOLATION
