# WP-015: Dedupe & history (DED-01/02/03, PRN-05)
Spec: DED-01/02/03, DM-01, PRN-05, PRN-01 · Phase: 1 · Tier: A · Depends: WP-014 (assign), WP-013 (normalize)

## Goal
A PURE `dedupeRun()` that flags repeat leads and pins them to their ORIGINAL partner,
never rewriting history (PRN-05). Runs after assignment; overrides the current-run
candidate assignment for repeats.

## Design
- Primary match = `dedupe_key` (normalized address + zip5, DM-01). Phone (last-10) is a
  secondary CONFIRM only — sets `phoneConfirmed`, never creates a match (owner-confirmed).
- History hit (prior run): `previously_matched=true`; assignment reverts to the original
  partner + method; `first_matched_at` carried (PRN-05 — current coverage never moves an old lead).
- Within-run duplicates collapse to the first occurrence (deterministic by file order).
- New lead: `previously_matched=false`, keep current assignment; `first_matched_at` stamped
  by the caller (WP-017) — engine stays pure (no Date.now, PRN-01), returns `firstMatchedAt:null`.
- Degenerate keys (missing address OR zip) are non-dedupable → always treated as unique
  (prevents false merges of missing-data rows).
- Nothing is dropped: kept/removed/unmatched/previously-matched all flow through (DED-03).

## Definition of done
- [ ] `src/modules/pipeline/dedupe.ts`: `dedupeRun(leads, history) → DedupeResult[]`, pure.
- [ ] Result carries `previouslyMatched, partnerId, matchMethod, originalPartnerId, firstMatchedAt, phoneConfirmed, duplicateOfIndex`.
- [ ] Extend the golden with a synthetic week-2 (some week-1 leads reappear) → assert prev-matched + original partner carried.

## Out of scope
Persistence + `first_matched_at` stamping + audit_log (WP-017); "possible duplicate by phone"
near-dupe flag (deferred candidate); void-run interplay (WP-018); the DB unique-index conflict
handling for degenerate keys (WP-017).

not merged · PRN-01 determinism. Plus the extended golden.
