| C-16 | **WP-KAN-1a** — LATERAL rewrite of the two correlated status subqueries + a covering index + push the column filter into `base` | WP-KAN-1 (audit-tenancy F-3 + pr-reviewer F-2) | `latestStatus`/`latestAt` (src/modules/leads/queries.ts) are per-row correlated subqueries evaluated once per lead, for BOTH the list and the board. The board makes it structural: `listLeadsBoard` builds `base` over the whole scoped, kept lead set and only slices with `row_number()` afterwards, so **cost scales with tenant size, not page size** — and a single-column "Load more" (`?status=X&page=2`, 25 rows) still pays a full-board scan because the status filter is applied after the window. Three parts, one WP: (a) replace both subqueries with one `LEFT JOIN LATERAL (select status, created_at from lead_status_history where lead_id = leads.id and <tenant> order by created_at desc, id desc limit 1) h on true` so the history is probed once per lead instead of twice; (b) add the covering index `lead_status_history (lead_id, created_at desc)` — today only `lead_status_lead_idx (lead_id)` exists, so every probe sorts; (c) push `col_status in (…)` down into `base` for the single-column path. **Alias trap:** the scope-aware fragments (`tenantWhere(schema.leads, …)`, `statusExpr`, every `${schema.leads.x}` ref) render the drizzle TABLE NAME, never an alias — which is why the CTE deliberately does `from leads` unaliased. A LATERAL rewrite that aliases `leads` (`from leads l`) will emit `"leads"."id"` inside a query where only `l` is in scope: it fails loudly on the board, but a partially-aliased WHERE could silently widen scope. Alias nothing, or convert every embedded fragment in the same pass. Measure first — the board is fast at current tenant sizes; this is a scaling item, not a bug. **Also fold in the portal's parallel copy:** `src/modules/portal/queries.ts` declares its OWN `latestStatus`/`statusExpr`, which did NOT get the `, id desc` tie-break the admin pair received in the WP-KAN-1 review fixes (portal code was out of that WP's scope). Until it does, a same-timestamp tie can read one way in the admin list/board and another in the partner portal. Same probe, same index, same tie-break — do all three call sites together. |
