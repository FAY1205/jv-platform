# WP-028b: Stored exports + signed-URL download + upload constraints (EXP-05, SEC-02/03)
Spec: EXP-05, SEC-02, SEC-03 · Phase: 2 · Tier: A · Depends: WP-020 (run/export), WP-023 (admin client)
## Goal
Store each run's rendered deliverable .xlsx in a PRIVATE bucket on completion, and
serve downloads via a short-lived signed URL (no public files); re-downloadable from
run history, with regenerate-on-download kept as a fallback. Enforce upload
constraints (extension + size + row cap) so a wrong/oversized file is rejected early.
## Definition of done
- [x] `src/modules/export/storage.ts` — `exportStoragePath` (pure), `ensureExportsBucket` (private, idempotent), `storeExport` (upsert), `signedExportUrl` (5-min TTL, forced-download filename)
- [x] `src/lib/upload-guard.ts` — `validateUploadFile` (SEC-03 extension + 10 MB), `MAX_UPLOAD_ROWS`
- [x] `POST /api/uploads` stores the rendered export + records `storage_path` (best-effort); row cap `MAX_UPLOAD_ROWS` (SEC-03)
- [x] `GET /api/runs/[ref]/export` → 302 to a signed URL when stored (SEC-02), else regenerate (fallback)
- [x] `/upload` page rejects an unsupported extension / oversized file before parsing (SEC-03)
- [x] Live-verified: storage round-trip integration test (store → signed URL → exact bytes; public URL refused = private); full app E2E (upload → 302 signed URL → 200 valid .xlsx; empty/invalid upload → 400)
## Out of scope (→ later WPs)
Storing the ORIGINAL uploaded file + retention (SET-07) → later (the client-parse flow posts rows, not a file). Server-side content-type sniffing of a raw file upload → n/a while parsing is client-side (extension + size + row cap cover it). ACC-03 full-org export → later. Signed-URL TTL as a setting → follow-up (fixed 5 min).
